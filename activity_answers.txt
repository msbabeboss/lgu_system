PART A. SYSTEM EXAMINATION
================================================================

QUESTION 1: What is the name of your system?
ANSWER:
Talavera LGU Information Management System (Talavera LGU IMS)

----------------------------------------------------------------

QUESTION 2: What problem does your system solve?
ANSWER:
The system addresses the inefficiency of manual, paper-based barangay records management in Talavera, Nueva Ecija. Before this system, barangay staff had to manually record resident information, process certificate requests, manage blotter cases, and generate reports using physical logbooks and paper forms. This caused delays, data duplication, lost records, and difficulty in generating accurate population reports. The system centralizes all barangay operations — resident profiling, household management, certificate issuance, blotter recording, and population forecasting — into one secure, digital platform accessible by authorized personnel.

----------------------------------------------------------------

QUESTION 3: Who are the intended users of your system?
ANSWER:
1. Super Admin (LGU-level administrator) — manages all barangays, users, system settings, and cross-barangay reports.
2. Barangay Admin — manages their assigned barangay's residents, households, certificates, blotter cases, officials, and other barangay-level records.
3. Future scope: Barangay Secretaries and Captains who may need read/view access.

----------------------------------------------------------------

QUESTION 4: What are the major features or modules of your system?
ANSWER:
1. Resident Management — add, edit, view, archive, and search resident profiles (including PWD, senior citizens, solo parents, 4Ps members).
2. Household Management — record and manage household information and household members.
3. Certificate Issuance — issue barangay clearances, certificates of residency, indigency, and other official certificates.
4. Blotter Case Management — file, track, and update barangay blotter cases with timeline and resolution tracking.
5. Officials Management — record and manage barangay officials and their terms.
6. Population Forecasting (ARIMA) — predict future population, blotter, and certificate trends using statistical modeling.
7. Analytics and Reports — visual charts and exportable reports for barangay statistics.
8. Transfer Management — handle resident transfers between barangays (outgoing and incoming).
9. Archive System — soft-archive deleted or inactive records for recovery.
10. Notifications (Real-time) — real-time bell notifications via Pusher for system events.
11. Email Notifications — automated email alerts via Gmail SMTP for key actions (certificate issued, blotter filed, new resident added, etc.).
12. Activity and Audit Logs — complete traceable logs of all user actions.
13. User Management (Super Admin) — create, deactivate, and manage system user accounts.
14. Two-Factor Authentication (2FA) — TOTP-based 2FA for enhanced login security.
15. Notices and Announcements — LGU-to-barangay notice broadcasting.
16. Requests System — barangay admins can submit requests (password change, edit access, etc.) to the super admin.

----------------------------------------------------------------

QUESTION 5: What programming languages, frameworks, database systems, and development tools did you use?
ANSWER:
- Programming Languages: PHP 8.x (backend), JavaScript (frontend logic), HTML5, CSS3
- Frontend Framework/Libraries: Bootstrap 5 (UI components), Bootstrap Icons, Chart.js 4.4.0 (analytics charts)
- Backend: Pure PHP (no MVC framework — procedural with helper functions), PDO for database access

- Development Tools: XAMPP (Apache + MySQL on Windows), VS Code / Kiro IDE
- Libraries/Packages (via Composer): PHPMailer (email), Pusher PHP SDK (real-time push)
- Remote Access: Tailscale (VPN tunnel), ngrok (temporary public URL)
- Version Control: Git

----------------------------------------------------------------

QUESTION 6: What type of system architecture does your system use? Explain your answer.
ANSWER:
The system uses a Three-Tier (3-Tier) Client-Server Architecture:

1. PRESENTATION TIER (Client/Frontend): The user interacts with the system through a web browser. The interface is built with HTML5, CSS3, Bootstrap 5, and JavaScript. AJAX (fetch API) is used for dynamic, non-page-reload interactions like searching residents or loading forecasts.

2. APPLICATION TIER (Backend/Business Logic): PHP scripts on the Apache web server (XAMPP) handle all business logic — authentication, form validation, data processing, PDF/Excel export, email sending, and real-time push notifications. A custom helper system (functions.php, auth.php, mailer.php, pusher.php) handles shared logic.

3. DATA TIER (Database): MySQL/MariaDB stores all persistent data — residents, households, certificates, blotter cases, logs, users, and barangay information. All database access goes through a PDO-based singleton class.

Additionally, a microservice-style Python Flask API (ARIMA forecasting) runs locally on port 5001 and is called by the PHP backend as needed, adding a lightweight service-oriented element to the architecture.

----------------------------------------------------------------

QUESTION 7: How do the user interface, application logic, and database communicate with one another?
ANSWER:
1. The user opens a page in their browser (e.g., residents.php). The browser sends an HTTP GET or POST request to the Apache server.
2. The PHP script on the server receives the request. It includes config.php, which sets up the database connection (PDO), loads session data, and checks user authentication/role.
3. For data retrieval, the PHP script runs a prepared SQL statement against the MySQL database via PDO and fetches the result set.
4. For dynamic interactions (search, forecast, resident lookup), the JavaScript frontend uses the fetch() API to call AJAX endpoints (e.g., /ajax/search_residents.php), which return JSON responses.
5. The PHP script builds the HTML response (or JSON for AJAX), sends it back to the browser, and the browser renders the result.
6. For real-time notifications: When an action occurs (e.g., new notification inserted), PHP calls the Pusher PHP SDK, which pushes the event to Pusher's cloud server, which then delivers it to the subscribed browser client via WebSocket.
7. For forecasting: The browser's fetch() calls /ajax/get_arima_forecast.php, which acts as a proxy and calls the local Python Flask API (http://127.0.0.1:5001), gets the JSON forecast result, and forwards it to the browser.

PART B. API INTEGRATION ANALYSIS
================================================================

QUESTION 1: Does your system currently use an API? If yes, identify it. If not, explain why.
ANSWER:
Yes. The system currently uses THREE APIs:

1. PUSHER API (https://pusher.com) — a cloud-based real-time messaging API used to deliver live notifications to users' browsers via WebSocket, without requiring a page refresh.

2. GMAIL SMTP API (via PHPMailer) — used to send automated email notifications (certificate issued, blotter filed, new resident, notice broadcast, password reset) using a Gmail account with App Password authentication.

3. LOCAL PYTHON ARIMA API (custom-built Flask server) — a locally hosted REST API running on http://127.0.0.1:5001 that performs ARIMA-based statistical forecasting on population, blotter, and certificate data.

----------------------------------------------------------------

QUESTION 2: What is the purpose of the API in your system, or what purpose could it serve?
ANSWER:
1. PUSHER API — Delivers real-time notifications to logged-in users instantly. When a super admin sends a notice or a new blotter is filed, the affected user sees a bell notification appear in their browser immediately, without needing to refresh the page. This improves the responsiveness and usability of the system.

2. GMAIL SMTP (Email API) — Provides automated communication outside the system. Barangay admins receive email confirmations when a certificate is issued, when a blotter case is filed, or when a new resident is added. Super admins receive email alerts on critical events. This ensures users stay informed even when not logged in.

3. ARIMA FORECAST API — Provides predictive analytics. Barangay admins and super admins can view projected future trends for population growth, blotter case frequency, and certificate issuance. This helps LGU officials plan resources and services in advance.

----------------------------------------------------------------

QUESTION 3: What data would your system send to or receive from the API?
ANSWER:

PUSHER API:
- SEND: { user_id, notification_id, message, type, created_at, category } — triggered from PHP when a notification is inserted into the database.
- RECEIVE: The Pusher client delivers the event payload to the subscribed browser WebSocket channel (private-user-{id}). No data is received back by PHP.

GMAIL SMTP (PHPMailer):
- SEND: Email content (HTML body, subject, recipient email address, sender credentials). Examples: password reset link, certificate details, blotter case summary, new resident data, notice content.
- RECEIVE: Boolean success/failure status. On failure, an error is logged.

ARIMA FORECAST API:
- SEND (PHP → Python): HTTP GET request with parameters: type (residents/blotter/certificates/all), barangay_id, months (forecast horizon), lookback (months of historical data).
  Example: GET http://127.0.0.1:5001/forecast/all?barangay_id=1&months=6&lookback=24
- RECEIVE (Python → PHP → Browser): JSON response containing historical data, forecasted values, ARIMA order (p,d,q), engine used (ARIMA or Holt's), trend direction, trend percentage, average values, and summary statistics.

----------------------------------------------------------------

QUESTION 4: What API endpoint, HTTP method, and data format are used or proposed?
ANSWER:

PUSHER API:
- PHP SDK method: $pusher->trigger('private-user-{id}', 'new-notification', $data)
- Auth endpoint: POST /ajax/pusher_auth.php (called automatically by Pusher JS to authenticate private channels)
- Data format: JSON
- Transport: WebSocket (Pusher handles the channel; PHP uses HTTPS to the Pusher REST API internally)

GMAIL SMTP:
- Protocol: SMTP over STARTTLS (not HTTP-based)
- Host: smtp.gmail.com, Port: 587
- Authentication: SMTP AUTH with username + App Password
- Data format: MIME (HTML email with UTF-8 encoding)

ARIMA FORECAST API (local Flask):
- Endpoint 1: GET http://127.0.0.1:5001/forecast?type={type}&barangay_id={id}&months={n}&lookback={n}
- Endpoint 2: GET http://127.0.0.1:5001/forecast/all?barangay_id={id}&months={n}&lookback={n}
- HTTP Method: GET
- Data format: JSON (response contains arrays of historical values, forecast values, ARIMA parameters, and summary statistics)

----------------------------------------------------------------

QUESTION 5: How does your system process the response received from the API?
ANSWER:

PUSHER:
The browser's JavaScript listens on the private Pusher channel using the Pusher JS SDK. When a 'new-notification' event arrives, the handler reads the event payload (message, type, category, id), appends a new notification item to the topbar notification dropdown, updates the unread badge count, and plays/shows the notification — all without any page reload.

GMAIL SMTP:
The PHP sendMail() function returns true on success or false on failure. The calling code (e.g., certificates.php) ignores the result to avoid blocking the main response, but all failures are logged via error_log() for debugging. The email delivery is treated as a non-critical side effect.

ARIMA FORECAST API:
The PHP proxy (/ajax/get_arima_forecast.php) receives the raw JSON string from the Python API using file_get_contents() and forwards it directly to the browser with the same HTTP status code. The browser's JavaScript then parses the JSON, extracts forecast values, labels, and trend data, and renders them as a Chart.js line chart with dashed lines for projected values. The summary panel below the chart displays trend direction, average values, ARIMA order, and engine used.

----------------------------------------------------------------

QUESTION 6: How would your system handle API errors, unavailable services, or invalid responses?
ANSWER:

PUSHER:
- If Pusher credentials are not configured, getPusher() returns null and pushNotification() exits silently (no-op). The notification is still saved in the database; the user will see it on next page load.
- Failed push attempts are caught in a try-catch and logged via error_log('[Pusher] trigger failed: ...').
- The system never crashes due to a Pusher failure — it degrades gracefully.

GMAIL SMTP:
- All sendMail() calls are wrapped in try-catch blocks. On failure, the error is logged but execution continues. Email delivery is treated as best-effort; critical business operations (like saving a certificate) are not blocked by email failures.
- In certificates.php, the certificate is saved and the JSON success response is sent to the browser BEFORE attempting to send the email, specifically to avoid SMTP blocking the response.

ARIMA FORECAST API:
- First, the PHP proxy tries to call the API with an 8-second timeout.
- If unavailable (connection refused), it attempts to auto-start the Python server using one of three methods: VBS launcher (silent background), pythonw.exe (no console window), or python.exe fallback.
- After auto-start, it waits up to 8 seconds (polling every 1 second) for the API to come up.
- If still unavailable, it returns HTTP 503 with a JSON error: { "error": "ARIMA API could not be started automatically.", "hint": "Please start it manually..." }.
- The browser displays a user-friendly error message: "Forecast failed. Please check if the ARIMA API is running."

----------------------------------------------------------------

QUESTION 7: What authentication, authorization, or data-protection measures are needed?
ANSWER:

AUTHENTICATION:
- Users log in with username + password (bcrypt hashed passwords).
- Optional TOTP-based Two-Factor Authentication (2FA) via Google Authenticator or similar apps.
- Sessions are managed with PHP session_start(), with httpOnly, secure, and SameSite cookie flags.
- Brute-force protection: login attempt counter, account lockout after too many failed attempts.
- Password reset via secure time-limited tokens sent to registered email.

AUTHORIZATION:
- Role-based access control (RBAC): pages check requireRole('super_admin') or requireRole('barangay_admin') at the top of every protected file.
- Barangay-scoped access: barangay admins can only access data from their assigned barangay_id.
- Pusher private channel authentication: /ajax/pusher_auth.php verifies that a user can only subscribe to their own private-user-{id} channel.

DATA PROTECTION:
- All database queries use PDO prepared statements with parameterized inputs, preventing SQL injection.
- CSRF tokens are used on all state-changing forms and AJAX calls (X-CSRF-Token header).
- Output is HTML-escaped with htmlspecialchars() before being rendered in the browser, preventing XSS.
- HTTPS is enforced via Tailscale tunnel; HSTS headers are sent when on HTTPS.
- Sensitive values (passwords, API keys, secrets) are stored in .env and never exposed in source code committed to version control (.env is in .gitignore).
- Pusher credentials: only the public key and cluster are sent to the browser; the secret stays server-side.
- Email: Gmail App Password is used (not the main account password) and stored only in .env.

QUESTION 8: What other system or service could be integrated with your project through an API? Why?
ANSWER:
A Philippine Statistics Authority (PSA) Data API or a PhilSys (National ID) verification API would be highly valuable. It would allow the system to verify a resident's identity against the national registry when adding a new resident, reducing data entry errors and preventing duplicate or fraudulent records. Since barangay records feed into national statistics, alignment with PSA data would improve accuracy and reduce reconciliation work during official census operations.

Additionally, a Google Maps / OpenStreetMap API could be integrated to visually plot household and resident locations on a map, helping barangay officials identify underserved areas, plan resource distribution, and respond faster to incidents by seeing blotter case locations on a map.

DATA FLOW:

GUIDE QUESTIONS (answered):

Why did you choose this architecture?
A three-tier architecture cleanly separates the user interface, business logic, and data — making the system easier to maintain, debug, and scale. The Python microservice for forecasting is kept separate because it uses a different runtime (Python) and can be scaled or replaced independently without affecting the PHP backend.

What happens when a user submits information?
The browser sends an HTTP POST to the PHP backend. PHP validates the input, runs a parameterized SQL INSERT/UPDATE via PDO, logs the activity, optionally triggers a Pusher push notification and/or sends an email via SMTP, and returns a redirect or JSON response to the browser.

How does data move between frontend, backend, database, and API?
Browser → HTTP/AJAX → PHP (business logic) → PDO → MySQL → result set → PHP builds HTML/JSON → Browser renders. For real-time: PHP → Pusher SDK → Pusher cloud → WebSocket → Browser. For forecasting: Browser → PHP proxy → Python Flask (localhost) → JSON → PHP → Browser → Chart.js.

Which component would be most affected if the API became unavailable?
If Pusher went down, real-time notifications would stop working, but the system remains fully functional — notifications are saved in the database and visible on page reload. If Gmail SMTP went down, email alerts would fail silently (logged only). If the Python ARIMA API went down, the Forecasting module would be unavailable, but all other modules continue working normally.

How could you improve the architecture for security, maintainability, or scalability?
- Use an MVC framework (e.g., Laravel) for better code organization.
- Move the Python forecasting API to a cloud server or containerize it with Docker.
- Add a message queue (e.g., Redis/RabbitMQ) for email sending to make it fully asynchronous.
- Implement API rate limiting and token-based authentication for AJAX endpoints.
- Add automated backups and database replication for the MySQL server.

PART D. RELEVANCE AND SIGNIFICANCE OF THE SYSTEM
================================================================

What specific problem in your community does your system address?
The system addresses the manual, paper-based record-keeping used by barangays in Talavera, Nueva Ecija. Barangay offices struggled with handwritten logbooks, physical certificate forms, and no centralized way to track residents, households, blotter cases, or officials. This caused delays in certificate requests, missing records, inability to generate accurate population counts, and difficulty reporting to the LGU. The system digitizes and centralizes all these operations into a single platform accessible by authorized staff.

How did you identify or validate this problem?
The problem was identified by observing actual barangay operations, interviewing barangay secretaries and staff, and reviewing existing manual records. The pain points — slow certificate processing, inability to search records quickly, and no way to see barangay-wide statistics — were directly reported by end users and confirmed during the needs analysis phase of the project.

Who will benefit most from your system, and how?
1. Barangay Staff (Admins/Secretaries) — processes that took 30+ minutes manually (searching records, writing certificates) now take under a minute.
2. Residents — faster, more accurate certificate issuance with less waiting time.
3. LGU Officials (Super Admin) — access to real-time data from all barangays, enabling better governance, resource planning, and decision-making.
4. Community Planners — ARIMA forecasting gives data-driven insights into population trends, helping plan for infrastructure and social services.

What makes your system different from existing systems or manual processes?
- Centralized: all barangay data in one platform, not scattered in paper logbooks.
- Real-time notifications via Pusher — immediate alerts without page refreshes.
- ARIMA-powered forecasting — proactive planning, not just reactive record-keeping.
- Multi-barangay support — one super admin manages multiple barangays under one system.
- Automated email alerts — staff are informed even when not logged in.
- Complete audit trail — every change is logged with who did it and when.
- Archive system — deleted records are recoverable.
- Secure 2FA login — much stronger than paper logbooks with no access control.

What evidence supports the usefulness of your system?
- Reduced certificate processing time from manual form-filling (15-30 minutes) to a few clicks.
- Complete digital records eliminate lost or illegible paper records.
- Audit logs provide accountability that manual logbooks cannot.
- The forecasting module provides data previously unavailable to barangay-level administrators.
- Email and Pusher notifications ensure critical events (new blotter, notice broadcasts) are never missed.

How does your system improve efficiency, accuracy, accessibility, decision-making, or service delivery?
- Efficiency: Batch operations (bulk export, search filtering) replace manual one-by-one processes.
- Accuracy: Duplicate detection (contact number checks), data validation, and prepared SQL statements prevent data corruption.
- Accessibility: Accessible from any device on the network (or remotely via Tailscale), not limited to one physical office.
- Decision-making: Analytics dashboards and ARIMA forecasting provide actionable insights previously unavailable.
- Service delivery: Residents receive faster certificate service; staff can check history instantly without digging through files.

What limitations or weaknesses remain in your current implementation?
- The Python ARIMA API runs locally on the server machine — it is not cloud-hosted and requires manual setup on each deployment environment.
- No resident self-service portal — residents cannot request certificates or check their own records online.
- No mobile-native app — the system is web-based and may not be fully optimized for mobile screen sizes in all modules.
- Email delivery depends on Gmail App Password, which can be revoked by Google without notice.
- The system is currently single-server — no load balancing or database replication for high availability.
- Limited offline capability — the system requires an active network connection.

If you had additional time and resources, what features or integrations would you prioritize?
1. PhilSys (National ID) API integration — for resident identity verification against the national registry.
2. SMS Notifications (via Semaphore or Vonage) — reach residents without email access.
3. Resident self-service portal — allow residents to request certificates online.
4. Cloud hosting and deployment — move from XAMPP to a production server (e.g., AWS, DigitalOcean) for 24/7 availability.
5. Mobile app (PWA or native) — for barangay staff to access the system on smartphones.
6. Google Maps integration — visualize household/resident locations and blotter incident hotspots.
7. Inter-barangay messaging — direct communication between barangay admins and the LGU.

What ethical, privacy, security, or legal concerns must be considered?
- Data Privacy Act of 2012 (RA 10173) — the system collects sensitive personal data (name, birthdate, address, classifications like PWD/4Ps). Users must be informed about data collection and the data must be protected with appropriate technical security measures.
- Access control — only authorized personnel should access resident data. The current RBAC system addresses this, but physical security of the server must also be maintained.
- Data retention — there must be policies for how long records are kept and when they should be purged.
- Consent — residents being profiled should ideally provide consent for their data to be digitally stored.
- Security of credentials — API keys, email passwords, and database credentials must be stored securely and rotated regularly.
- Audit accountability — the activity and audit logs ensure there is a traceable record of who accessed or modified data.

If your system were adopted by a real organization, what would be necessary to deploy, maintain, and support it?
- Server infrastructure: A dedicated server or cloud hosting (with SSL, backups, and monitoring).
- Database backup policy: Automated daily backups with off-site storage.
- Staff training: Barangay staff would need orientation on using the system properly.
- IT support: A technical person or team available for bug fixes, updates, and troubleshooting.
- Data migration: Existing paper records would need to be encoded into the system.
- Legal compliance review: Ensure the system complies with RA 10173 and any relevant DICT/DILG guidelines for LGU digital systems.
- Update and maintenance cycle: Regular updates for security patches and feature improvements.

PART E. INTEGRATION PROPOSAL
================================================================

Proposed API or External Service:
Semaphore SMS API (https://semaphore.co) — a Philippine SMS gateway API

Purpose of Integration:
To send SMS notifications directly to residents and barangay staff's mobile phones when important events occur — such as certificate readiness, blotter case updates, or LGU notices — reaching people who may not have email access or may not be logged into the system. This is especially important in rural barangays in Talavera where internet access may be limited but mobile phones are widely available.

Data to Be Exchanged:
- SEND to Semaphore API:
  { "apikey": "[API_KEY]", "number": "09XXXXXXXXX", "message": "Your Barangay Clearance is ready for pickup. - Talavera LGU", "sendername": "TalaveraLGU" }
- RECEIVE from Semaphore API:
  JSON response with message_id, status (Queued/Sent/Failed), and recipient number confirmation.

API Endpoint and Documentation:
- Endpoint: POST https://api.semaphore.co/api/v4/messages
- HTTP Method: POST
- Data Format: JSON (application/json) or application/x-www-form-urlencoded
- Official Documentation: https://semaphore.co/docs
- Authentication: API Key passed as a parameter (apikey field in the POST body)
- Rate limit: varies by plan (typically 100-1000 SMS/day on free/paid tiers)

Expected Benefit to Users:
- Residents are notified via SMS when their certificate is ready for pickup — no need to physically return to the barangay office to check.
- Barangay staff receive SMS alerts for critical events (new blotter, urgent notices) even when not at their computer.
- The system becomes accessible to residents and staff even without internet access, bridging the digital divide common in rural municipalities.
- Reduces phone-in inquiries to the barangay office.

Technical Requirements:
- A Semaphore account with an active API key and SMS credits.
- A PHP function (sendSMS()) using cURL or file_get_contents() to POST to the Semaphore endpoint.
- Residents' and users' mobile phone numbers must be stored in the database (already collected in the residents and users tables).
- The API key must be stored in .env (SEMAPHORE_API_KEY) and never hard-coded.
- SMS sending should be asynchronous (fire-and-forget) to avoid slowing down the main request, similar to how email is handled.

Security and Privacy Considerations:
- The API key must be stored in the .env file and excluded from version control (.gitignore).
- Phone numbers are personal data under RA 10173 — they must only be used for legitimate system notifications and never shared with third parties.
- Outgoing SMS content must not include sensitive information (e.g., no passwords, no case details) — only general notifications with a link or instruction to log in.
- Rate limiting should be implemented to prevent accidental SMS flooding (e.g., max 1 SMS per event per user per hour).
- Opt-out mechanism: Residents should be able to opt out of SMS notifications.

Possible Limitations or Risks:
- Semaphore charges per SMS — high-volume barangays may incur significant costs.
- The registered sender name ("TalaveraLGU") must be pre-approved by Semaphore, which takes time.
- SMS delivery is not guaranteed (network issues, invalid numbers, phone off).
- International numbers are not in scope — this is a Philippines-only service, which is acceptable for this system.
- Requires residents to have a valid registered mobile number in the system (currently stored but not always verified).

Expected Outcome After Integration:
